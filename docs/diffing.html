How the DOM Diff Works

BrickPHP renders both sides of a change on the server and ships the difference. This document follows one interaction end to end: how a component becomes a tree of DOM nodes, how that tree becomes HTML, and how two of those trees are compared into a list of patch operations the browser can apply.

1The idea in one paragraph

Most component frameworks diff in the browser: the client keeps a virtual DOM, re-renders it after a state change, and compares new against old. BrickPHP keeps nothing in the browser. When an event fires, the server renders the tree twice in the same request — once for the state as it was before the event (OLD), once for the state after the handler ran (NEW) — compares those two server-side trees, and returns a flat list of patch operations. The browser's only job is to apply them.

The consequence that shapes everything else The server never looks at the real DOM. It infers what the browser is showing by re-deriving it from persisted state. So OLD must be an exact reproduction of what is on screen — which is why the framework carries a state hash, replays the previous URL, and falls back to a full reload the moment those assumptions break (§9).

2The request lifecycle

2.1  First load — a GET

The entry App renders once in RenderPhase::Initial, state is persisted, every event listener in the tree is bound, and a full HTML document goes out. A hash of the state is embedded as window.__BRICK_HASH; the client echoes it back on every subsequent POST. 

// Brick::handleGet — src/Brick.php:960
$ui = $entry->render($state, null, RenderPhase::Initial);
$entry->finalize($state);          // persist component state
$ui->bindEvents();                 // queue client-side listener wiring
$stateHash = self::computeStateHash($state);   // sha1(serialize(all state))

Three details in that sequence are easy to miss and matter a great deal:

  • The event runs against the OLD tree. findByPath($path) locates the node the user actually clicked in the tree as it was rendered — the handler closure lives on that node.
  • The OLD render is done at previousPath, not the current URL. After a popstate the browser URL has already moved on; without the override, OLD would render the new route too, the diff would come out empty, and the stale DOM would never be patched.
  • finalizeAll sweeps every component, not just the event's owner. A handler can capture $this from an ancestor and mutate its state; finalizing only the owner would silently drop those writes.

2.3  The three render phases

3How a component is built

There are two trees, and keeping them apart is the key to reading the codebase. The VNode tree — components and fluent UI builders — is scaffolding that exists only during a render. It produces the DomNode tree, and that is the artifact that gets serialised to HTML and diffed. Nothing above DomNode ever takes part in the compare. 

  VNode  (transient — rebuilt every render)          DomNode  (the diffable artifact)
  ────────────────────────────────────────           ───────────────────────────────
  App              extends Component

3.1  The build → render contract

Every component implements one abstract method, build(): VNode, returning the subtree for its position. The framework calls render(), which wraps build() in identity resolution, state restoration and lifecycle:

3.2  Component identity: path:class

A component is identified by getStateKey() — its path joined by dots, a colon, and its concrete class name (e.g. 0.1.2:Samples\FlagQuiz\Components\ScoreBar). That single string does a lot of work:

  • It is the storage key for the component's state in the StateManager.
  • It matches the OLD instance to the NEW instance so shouldRender($old) has something to compare against.
  • array_diff_key($oldRegistry, $newRegistry) is literally how deleted() is computed — a component present in OLD but absent from NEW is gone, and its bound state is dropped from storage.
Implication Component identity is positional. Move a component to a different index and the framework sees the old one deleted and a new one created — its state resets. This is the same trade-off that makes key() matter for lists (§6.4).

4Paths: the addressing scheme

A patch is useless without a way to say where. BrickPHP addresses every node by its positional path from the root — an array of child indices, [0, 3, 1] meaning "root → child 0 → child 3 → child 1". 

// DomNode::assignPaths — src/UI/DomNode.php:94
public function assignPaths(array $parentPath = []): static
{
    $this->path = $parentPath;
    $this->managed = true;
    $this->assignChildPaths();      // child i gets [...$this->path, $i]
    return $this;
}

Assignment happens exactly once per render, in a single pass from the true root ($parent === null). Doing it per-node would make path assignment O(n²) — every node re-walking its own subtree.

The same path array is used for four different things, which is what keeps the system coherent:

  1. Patch targets — every operation carries the path of the node it acts on.
  2. Event addressing — the client posts the path of the element that was clicked; the server finds the handler with findByPath().
  3. Listener binding — each EventRegistration is added or removed at a path.
  4. Component identity — the path:class state key of §3.2.
Why text is wrapped in a span The client resolves paths by walking element.children, which skips text nodes. If bare text nodes were allowed into the tree, server-side indices (which counted them) and client-side indices (which didn't) would drift apart, and every patch after the first text node would land on the wrong element. Wrapping text in a <span> keeps a single, unambiguous indexing scheme on both sides.

5How the HTML is built

Serialisation is a plain recursive toHtml() over the DomNode tree. It runs in two situations: for the whole tree on the initial GET, and for individual subtrees that a patch needs to insert or replace. In the second case it happens after the diff, when the collected operations are handed out: 

// Patcher::getOperations — src/VNode/Patcher.php:150
return array_map(function ($op) {
    if (isset($op['node']) && $op['node'] instanceof DomNode) {
        $op['html'] = $op['node']->toHtml();     // serialise only what's actually sent
        unset($op['node']);
    }
    return $op;
}, $this->operations);

That ordering is deliberate: a node that the diff decides is unchanged is never serialised at all.

What lands in the markup

  • Classes are self-describing utility names, merged from the node's own class list and any explicit class attribute, then de-duplicated. The client decodes unfamiliar names into real CSS rules as patched HTML arrives — so no stylesheet payload rides along with the patches.
  • No inline on* handlers. Every listener is wired imperatively through its EventRegistration, driven by the diff (§8).
  • Wireframe metadata (data-wf-label, data-wf-file, data-wf-line) is emitted straight into the attribute string and deliberately kept out of the node's $attributes array — so the diff never sees it and dev-mode annotations can never generate patches.
  • Void elements (img, input, br, …) are looked up in a keyed constant and closed without a child list.

6The compare

Everything below hangs off one abstract method: 

// src/UI/DomNode.php:183
abstract public function compare(DomNode $other, Patcher $patcher): void;
Read this before reading the source The call is $newUi->compare($oldUi, $patcher). Inside every compare() implementation, $this is the NEW node and $other is the OLD one. Reversing them in your head inverts the meaning of every insert and delete.

6.1  The order of checks in TagDomNode::compare

src/UI/TagDomNode.php:551

// 1. Opted out entirely — don't even walk the subtree.
if ($this->frozen) { return; }

// 2. Different node type or different tag → wholesale replacement.
if (!$other instanceof TagDomNode || $this->tag !== $other->tag) {
    $other->unbindEvents();
    $patcher->replaceNode($this->path, $this);
    $this->bindEvents();
    return;
}

// 3. A whole-node invalidation cascades to every child.
if ($this->invalidated) {
    foreach ($this->children as $child) { $child->setInvalidated(true); }
}

// 4. Attributes: present-and-different, or forced → set. Vanished → remove.
foreach ($thisAttrs as $name => $value) {
    $forced = $this->invalidated || isset($this->invalidatedAttrs[$name]);
    if ($forced || !isset($otherAttrs[$name]) || $otherAttrs[$name] !== $value) {
        $patcher->setAttribute($this->path, $name, $value);
    }
}
foreach ($otherAttrs as $name => $value) {
    if (!isset($thisAttrs[$name])) { $patcher->removeAttribute($this->path, $name); }
}

// 5. Classes are compared as a whole and re-emitted as one attribute.
if ($classForced || $thisClasses !== $otherClasses) {
    $patcher->setAttribute($this->path, 'class', $this->serializeClasses($thisClasses));
}

// 6. This element survived, so diff its listeners rather than rebinding them.
$this->diffEvents($other);

// 7. Recurse.
$this->compareChildren($other, $patcher);

Note step 2: a replacement is structural, not incremental. The whole subtree is serialised and shipped, so a changing tag name is the most expensive thing the diff can encounter. Text is cheaper — TextDomNode::compare emits a single replace_text when the content differs, and falls back to replace_node only if the OLD node wasn't text at all.

6.2  Choosing a child strategy

Children are compared positionally unless both the old and new child lists are fully keyed — every single child carrying a non-null key: 

// TagDomNode::compareChildren — src/UI/TagDomNode.php:630
$newKeyed = $this->childrenAreKeyed();
$oldKeyed = $other->childrenAreKeyed();

($newKeyed && $oldKeyed)
    ? $this->compareChildrenKeyed($other, $patcher)
    : $this->compareChildrenPositional($other, $patcher);

One unkeyed child in a list of a hundred silently downgrades the whole list to positional comparison.

6.3  Positional comparison

Index i in NEW is compared against index i in OLD. Surplus old children are deleted in reverse order — deleting forwards would shift the indices of everything still to be removed. 

  OLD   [ A ][ B ][ C ][ D ]        NEW   [ A ][ X ][ C ]

        i=3  delete_node [.,3]      ← reverse order first
        i=0  A vs A → recurse, no change
        i=1  B vs X → recurse, patches
        i=2  C vs C → recurse, no change

6.4  Keyed comparison

src/UI/TagDomNode.php:683

Each key maps to a FIFO queue of the old indices that carry it. Walking the new children in order, the algorithm accepts the next candidate for a key only if its old index is strictly greater than the last index it matched; otherwise the candidate is discarded and it tries the next one. A new child that finds no usable candidate becomes a fresh insertion. 

$oldQueues = [];
foreach ($other->children as $i => $child) { $oldQueues[$child->getKey()][] = $i; }

$lastMatched = -1;
foreach ($this->children as $newIdx => $newChild) {
    $key = $newChild->getKey();
    // discard candidates that would require moving backwards
    while (!empty($oldQueues[$key]) && $oldQueues[$key][0] <= $lastMatched) {
        array_shift($oldQueues[$key]);
    }
    if (empty($oldQueues[$key])) { $matched[$newIdx] = null; continue; }   // → insert
    $oldIdx = array_shift($oldQueues[$key]);
    $matched[$newIdx] = $oldIdx;
    $usedOld[$oldIdx] = true;
    $lastMatched = $oldIdx;
}

The strictly-increasing rule is what lets the diff produce correct DOM order without ever emitting a move operation. Anything that would have to travel backwards is expressed as a delete plus an insert instead.

The trade-off, stated plainly There are no move patches. Reordering a list — dragging a row upward, reversing a sort — is realised as removal and re-insertion, so any DOM state living in those elements (focus, scroll position, an in-progress text selection, CSS transitions) is lost. Appends, removals and in-place edits are handled optimally; reordering is correct but not cheap.

6.5  ListDomNode and the Levenshtein alignment

ListDomNode takes a different route. It reduces both child lists to arrays of keys and runs a modified Levenshtein edit-distance over them, then walks the resulting DP table backwards to recover the edit script. 

// Levenshtein::populate — src/Dom/Levenshtein.php:19
$neighbours = [
    [$dp[$i-1][$j-1][0] + ($same ? 0 : 1), ($same ? self::SKIP : self::SUBSTITUTE)],
    [$dp[$i-1][$j][0],                      self::DELETE],
    [$dp[$i][$j-1][0],                      self::INSERT],
];
$min = array_reduce(
    $neighbours,
    fn($acc, $item) => $item[0] < $acc[0] ? $item : $acc,
    $neighbours[0],
);
$dp[$i][$j] = [$min[0] + ($same ? 0 : 1), $min[1]];

The four action codes map directly onto patch operations:

ActionMeaningWhat ListDomNode::compare does
SKIPKeys matchRecurse into the pair — $newItem->node->compare($oldItem->node, …)
SUBSTITUTEKey changed at this slotupdate_at; unbind old listeners, bind new
INSERTPresent only in NEWinsert_at; bind the new subtree's listeners
DELETEPresent only in OLDremove_at at an offset-adjusted index; unbind

The edit script comes back reversed (the traversal runs from the bottom-right of the table toward the origin), so it is array_reversed before being applied. Two counters run alongside: $newIndex advances on everything except a delete, and $removeOffset compensates for indices already removed.

A hard limit worth knowing The backtrace loop in Levenshtein::diff is bounded by a literal $count = 20. Since recovering the script takes roughly max(count(OLD), count(NEW)) steps, a ListDomNode holding more than about twenty children stops emitting operations before it reaches the start of the list — the earliest items produce no patches at all. TagDomNode's keyed path (§6.4) has no such bound, which makes it the safer choice for long lists today.

7The patch protocol

The diff's entire output is a JSON array of operations. Nine types exist; each carries a path, and the ones that add markup carry pre-serialised html.

Resolution on the client is the mirror image of assignPaths:

// assets/brick.js:91
function findNodeByPath(path, includeTextNodes = false) {
    let node = document.body.firstElementChild;      // the root element
    for (let i = 0; i < path.length; i++) {
        if (!node) return null;
        node = includeTextNodes ? node.childNodes[path[i]] : node.children[path[i]];
    }
    return node;
}
Order is load-bearing Patches are applied strictly in the order the server emitted them, and each one is resolved against the DOM as mutated by its predecessors. This is why deletions are emitted in reverse index order and why the list algorithms carry offset counters — the server is reasoning about a moving target.

8Event binding rides the diff

There is no separate pass to reconcile listeners. Registration and de-registration are emitted by compare() itself, at exactly the moments a node's participation in the tree changes:

SituationListener handling
Node replaced (type/tag change)$other->unbindEvents() then $this->bindEvents() — whole subtrees
Child insertedbindEvents() on the new subtree
Child deletedunbindEvents() on the departing subtree
Node survivesdiffEvents($other) — bind only listeners that appeared, unbind only those that vanished
// TagDomNode::diffEvents — src/UI/TagDomNode.php:258
foreach ($this->events as $event => $data) {
    if (!isset($old->events[$event])) { $data['registration']->add($this->path); }
}
foreach ($old->events as $event => $data) {
    if (!isset($this->events[$event])) { $data['registration']->remove($this->path); }
}

An unchanged listener on a surviving node is left strictly alone — it is neither rebound nor re-emitted, which is what keeps a re-render from disturbing in-flight interactions.

9Controlling and constraining the diff

9.1  The four escape hatches

MechanismSet withEffect
frozensetFrozen()Diff bails at this node. No attributes, text or children compared; the subtree isn't even rendered during a POST. For genuinely static UI.
invalidatedinvalidate()Force-emit patches regardless of equality, cascading to every descendant. For values the server-vs-server diff structurally cannot see as changed.
invalidatedAttrsinvalidateAttr($n)The same, narrowed to one attribute; everything else diffs normally.
shouldRenderoverride on a componentReturning false substitutes a NoOpDomNode, skipping both build() and the diff for that subtree.
Why invalidate() has to exist OLD and NEW are rendered milliseconds apart in the same request, so anything derived from the clock, from randomness, or from an external source produces the same value on both sides. The diff correctly concludes "no change" — while the browser is still showing a value from a render minutes ago. A clock's hands are the canonical case: they must be force-patched because the server has no way to notice they moved.
Why shouldRender() defaults to true Returning false from a parent also skips every descendant's build(). A child's own state can change without touching the parent's, and the parent would never see it — so a false default would be unsound. Memoization is safe to opt into on leaves (hasChanged($old) compares serialized state snapshots taken before any handler ran), and needs care above them.

9.2  Guarding the assumption that OLD is accurate

The whole design rests on the server being able to reproduce the user's screen. Three mechanisms defend that:

  • The state hash. The client echoes the sha1(serialize(all state)) it was rendered against. If the server's current state hashes differently — another tab mutated it, a deploy reshaped it — the response is {success: false, reload: true} rather than a patch list computed against a tree the user isn't looking at.
  • previousPath. The URL the DOM was last rendered for, used to render OLD after the browser has already moved the address bar (§2.2).
  • Blanket recovery. If restoring serialized state throws during either render — typically because the persisted shape no longer matches the current code — all state is cleared and the client is told to reload into a clean default.

9.3  Cost model

OperationCost
Text changeOne replace_text. Cheapest possible patch.
Attribute or class changeOne set_attribute per changed attribute; classes go as a single merged string.
Tag or node-type changeWhole subtree serialised and shipped. Most expensive.
Append / remove in a keyed listOne operation per affected item.
